# "seqlz, line by line": first read in order, consistency report

Book: `/home/martinus/gra/quetschn/wisebike/docs/book/` at `34e8002` (src identical to `a2d57dd`).
All paths below are relative to `docs/book/chapters/`; `file:line` is the line in the `.md` file.

## How this was checked

- Read all 19 chapters in `book.json` order, completely, with notes per chapter.
- Ran, in a scratch directory, every "Try it" box and every worked example that has a program
  or numbers that can be recomputed. All of these reproduce exactly:
  - ch2 example page `cat=1,dog=2;cat=3,dog=4;`: 28 bytes, `... 32 0c ca 59 9f 98 fb f1 22 80`;
  - ch4 page of `ab`: `02 00 61 62 dc 65 ef db 8a`, `seqlz_ref.py` prints `valid 2c888a...7a3`; ch4
    second page, 26 bytes, byte for byte;
  - ch5 clang/gcc prefetch box; ch6 constants program (`0x95C840 25 7`, and the 16 KiB line);
  - ch7 `token_entry()` program (`0x0393bec9 ...`); ch8 table-hash Python (`8348c354...`, 576, 1.0);
  - ch9 `find.c` (511 sequences, rows as printed); ch10 `ab.c`; page of pointers 817 bytes;
  - ch11 example (151 bytes; 190 letters stay raw, 195 coded);
  - ch15 `test/seqlz_endian.c` output `fda8f1567c2bb3a1`;
  - ch16 `trace.c` + the `sed` for `dec_counted.c`: the whole output is identical to the book's;
    the "without the text" variant gives 395 bytes as stated.
- Built a copy of the book in scratch (`build.py --check`): no `not covered:`, no `warning:`;
  `lint.py` prints nothing.
- Checked suspicious numbers against `docs/explored-designs.md`, `docs/seqlz.md`, `docs/plan.md`.

The technical content is in good shape: I found two plain errors (C2, C3 below) and no wrong
explanation of C. The problems are structural: the order of the book, repetition, and numbers that
are each right but contradict each other on the page because the book does not say which
measurement each one is.

## Ranked findings (most harm to a reader first)

1. **Part I teaches Part II's code before the format exists** (flow, reading cost). `03-cpu.md`
   (11 589 words, 7 516 of prose) shows 7 listings of `src/` and explains them line by line:
   `seqlz_decompress.c` 7-26, 229-243, 291-298, 500-514, `seqlz.h` 186-206, `page_lz.h` 124-149,
   `seqlz_compat.h` 163-169. They need token entries (ch7), length values and `LL`/`ML` tables
   (ch4), the fast path (ch14), `FAST_IN_ROOM`, `skip`, `TOK_*`: e.g. 03-cpu.md:493 "The four lines
   inside the `if` are the refill of `seqlz_br_refill()` without its check that 8 bytes of input are
   left: the fast path runs only where they are, see `FAST_IN_ROOM` below". All 7 come back in Part II
   with the same explanation (13 overlapping listings in all, see section 2). A newcomer gets the
   hardest code of the book in chapter 3 and then the same code again.
2. **About 11 000 words of the same explanation in two to five places** (section 2), plus
   `17-decisions.md`, whose per-topic prose (about 6 300 words of its 11 162) restates the "why"
   boxes of Part II with the same numbers. The 8-vs-4 streams numbers appear 4 times, the 1/16 + 51
   rule with its measured box 4 times, `91fa53e` / "4656 of 4656" 5 times, the licence line 7 times.
3. **Wrong unit: "0.3 and 4.6 points"** (contradiction, wrong). 02-compression.md:604 "made writes
   13% and 15% slower for pages 0.3 and 4.6 points smaller", and 04-format.md:799-800 "for 0.3 and
   4.6 points less". The book defines a point as "1% of the page, 41 bytes" (02-compression.md:215,
   04-format.md:396, glossary:246). The source, explored-designs.md:5433: "the pages 2.7 and 60.6
   bytes smaller, 0.3% and 4.6%", i.e. percent of stored size, 0.07 and 1.5 points. 17-decisions.md:190,
   802 and 909 say it right ("0.3% and 4.6%", "2.7 and 60.6 bytes"). `docs/seqlz.md` lines 567, 766,
   873, 931 have the same error; the writers copied it.
4. **Wrong: "7% more"** in the format table. 17-decisions.md:237: "22% fewer decode cycles for the
   lengths, 7% more for the offset class". Two lines up, 17-decisions.md:225: "putting the offset
   class into the token as well cut it from 8758 to 8168 cycles, 7%". It is 7% fewer.
5. **The worst case is given as two different ratios, without the metric** (contradiction on the C6
   claim). 01-zram.md:364-366: "The slowest page found decodes in 1.33 times the p99 time of real
   pages on the phone's small core, where `lz4`'s slowest takes 1.57 times its own". 14-decode.md:585:
   "the costliest pages found decode in 1.59 times that p99 with `seqlz-fast-lit`; the same search
   found 2.58 times for `lz4`". Both are right (explored-designs.md:3192-3194 is A55 time, :3238-3244
   is instructions); 17-decisions.md:725-728 gives both and says which. ch1 and ch14 should name the
   metric.
6. **Chapter 2 ends with chapter 4's material.** 02-compression.md:607-626 takes the 28-byte page
   apart bit by bit: "the escape, then token 524 in 12 bits", "`111101` `11111000100` | the length value
   4036: `ml` = 35 + 4036". Token packing (`ll + 16 × (ml − 4) + 512 × class`), length values and the
   2-byte header are first explained in ch4; this table has no link to ch4. Token 49 at
   02-compression.md:490 has the same problem. Move the example to the end of ch4 (it is the same
   kind of walk as ch4's two examples) or link `#ch-format--token` and `#ch-format--length-values`.
